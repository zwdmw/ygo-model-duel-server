# 赛事系统使用说明

本系统由一个“联赛房间”管理赛程和积分，同时为每个选手配对创建独立的原生对局房间。3 人联赛会一次创建 3 个对局房间；4 人、5 人、6 人分别创建 6 个、10 个、15 个对局房间。

## 一、管理员创建联赛

1. 打开赛事网页，进入“创建赛事房间”。
2. 房间类型选择“`K 人循环联赛`”。
3. 输入 `K` 和选手名单。名单必须每行一人，人数必须与 `K` 相同。
4. 选择赛制：
   - `BO2`：每个配对房间打设定组数，每组 2 局，双方各先手一次。
   - `按实际局数`：每个配对房间打设定局数，每局新种子，双方逐局交换先手。
5. 循环赛需要镜像去运气时，BO2 选择“同种子换位”；需要每局重新洗牌时，选择“异种子换位”。
6. 牌局引擎选择“`MDPro3 / YGOPro2 真人对局`”。
7. 如需冠军和真人挑战者打决赛，填写“循环赛冠军挑战者”，并选择 BO7 结束方式：
   - `先赢 4 局立即结束`：任一方达到 4 胜就结算。
   - `不管胜负固定打满 7 局`：即使一方提前达到 4 胜也继续打满 7 局，最后按胜场决定冠军；若胜场相同则继续单局加赛。
   两种方式均为每局异种子、A/B/A/B 交替先手。
8. 点击“创建房间”。页面会显示每位选手的专属入口令牌，只显示在创建结果中，管理员应分别发送给对应选手。
9. 点击“开始比赛”。联赛的所有配对房间会同时进入进行中状态。

## 二、选手进入比赛

1. 使用管理员发送的房间编号和专属令牌进入选手页面。
2. 选手页面只显示本人参与的配对房间连接信息，不会显示其他选手的密码。
3. 在对应配对房间中点击“准备本局”。
4. 使用页面显示的主机、端口和连接码，在 MDPro3/YGOPro2 中加入该原生房间。
5. 第一局结束后，系统记录真实引擎结果并自动推进下一局。连续系列赛使用同一个原生房间，不需要返回服务器页面。
6. 主动离房或网络中断时，使用原选手连接码重新连接；连续系列赛未结束前，系统始终保留原席位和原生身份。

同一名选手可能同时参与多个配对房间，因此每个配对房间的连接码必须按房间分别使用。

## 三、观战

网页观战：

1. 打开房间的观战链接。
2. 页面显示实时总积分、每个配对房间的局分、状态和赛程。
3. 管理员为原生房间建立会话后，每个对局卡片会显示该房间的原生观战地址、端口和观战密码。
4. 进行中的原生房间会在双方用户名下显示 `在线`、`尚未连接`、`已断线，等待重连`、`已退出 / 断线` 或 `疑似卡住`，并显示最后通信或断线时长。

MDPro3/YGOPro2 原生观战：

1. 选择要观看的配对房间。
2. 使用该房间卡片显示的主机、端口和观战密码加入。
3. 不同配对房间的观战密码不同，不能混用。

## 四、积分和晋级

循环赛中：

- BO2 胜者 3 分，败者 0 分，BO2 平局双方各 1 分。
- 按局数模式中，每局胜者 3 分，平局双方各 1 分，败者 0 分。
- 所有配对房间完成后，系统按总积分排序并显示第 1 至第 `K` 名。
- 同分时依次参考 BO2 胜场、局差、局胜数和用户名排序。
- 如果设置了真人挑战者，第 1 名自动进入真人决赛；否则保留系统兼容的前两名决赛流程。

## 五、管理员操作

- `开始比赛`：一次激活联赛的全部配对房间。
- `比赛连接信息`：查看所有原生配对房间的选手码和观战码。
- `当前观战参数`：查看指定当前对局的原生观战信息。
- `重新生成入口`：重新生成所有选手入口，旧令牌立即失效。
- `关闭房间`：关闭所有未完成配对，保留历史比分；原生会话会一并关闭，房间不可恢复。
- `暂停/恢复`：建议只用于手工记分房间。原生牌局进行中时，系统会拒绝暂停，避免破坏引擎状态。
- `疑似卡住`：表示座位 TCP 仍连接，但牌局进行中连续 120 秒没有协议通信；它不会自动判负。先确认双方客户端和模型日志，重连失败后再展开“判罚结算”。
- `已断线，等待重连`：表示原席位仍保留，选手可继续使用原主机、端口和连接码返回，不需要新建房间。
- `强制结束并指定积分`：仅用于进行中的循环赛配对。填写双方最终总积分和原因后立即完成该配对；最后一个配对完成时，系统继续生成冠军决赛。

## 六、管理员 API 示例

创建 5 人、每个配对 10 个 BO2 的原生联赛：

```bash
curl -X POST http://127.0.0.1:8787/api/rooms \
  -H 'Content-Type: application/json' \
  -H 'X-Tournament-Admin-Key: ADMIN_KEY' \
  -d '{
    "name": "Sky Striker Top 5",
    "room_type": "league",
    "player_count": 5,
    "players": ["A", "B", "C", "D", "E"],
    "base_bo2_count": 10,
    "series_format": "bo2",
    "seed_mode": "mirrored",
    "engine": "native-pvp",
    "final_opponent_name": "真人挑战者",
    "final_completion_policy": "play_all_seven"
  }'
```

开始联赛：

```bash
curl -X POST http://127.0.0.1:8787/api/rooms/ROOM_ID/start \
  -H 'X-Tournament-Admin-Key: ADMIN_KEY'
```

查看总积分和所有配对房间：

```bash
curl http://127.0.0.1:8787/api/rooms/ROOM_ID
```

管理员查看所有原生连接信息：

```bash
curl 'http://127.0.0.1:8787/api/rooms/ROOM_ID/native-access' \
  -H 'X-Tournament-Admin-Key: ADMIN_KEY'
```

## 七、端口建议

- `8787`：赛事 HTTP、网页、API 和 WebSocket，建议只通过 Nginx/HTTPS 对外。
- `8790`：PvP 内部 HTTP，保持回环监听。
- `6009`：MDPro3/YGOPro2 原生 PvP 连接端口，只有需要真人或原生观战时开放。
- `6008`：现有模型桥接端口，按已有部署规则管理。

不要把 `8787` 的管理接口、`8790`、训练端口或 Evolution 内部端口直接暴露到公网。管理员密钥未启用时，必须用 Nginx、VPN、白名单或其他网络层保护管理页面。

## 八、录像归档与故障处理

- 页面连接状态每 5 秒同步一次。断线状态来自真实座位连接；“疑似卡住”是长时间无协议通信告警，不等同于引擎已经确认故障。
- 模型卡死、超时且重连失败时，管理员可在对应房间展开“判罚结算”，选择判负选手、判罚范围和原因。“剩余赛程判负”会保留已完成局；“整场所有局判负”会改判已完成局并补齐未打局。
- 判罚或强制积分结算会封存该房间当前的原生 PvP 会话，断开选手并禁止继续进入，但不会注销原观战码。判罚模式仍按既定种子和先后手计划写入带标记的弃权局；强制积分模式只覆盖该配对的最终联赛积分，不改写真实牌局。
- 封存后，系统只保留已经正常结束的真实局，正在进行但未结束的当前局不会计入录像。已保存的逐局 YRP 会在后台恢复为完整或部分系列录像；恢复完成后，观众仍使用原主机、端口和观战密码进入回放。
- 若封存前一局都没有完成，页面显示暂无录像；若部分已完成局缺少可验证的 YRP，页面显示录像不完整和缺失局号，不会伪造录像。
- 判罚记录会显示在管理员和公开赛事页面。若其他比赛结果尚未继续写入，管理员可撤销最近一次判罚；否则系统拒绝撤销，防止覆盖后续赛果。
- 连续对局的 YRP2 录像按原始种子、开局时间和已完成局记录匹配，不再直接使用接收队列中的局号。镜像 BO2 两局种子相同，必须同时核对时间。
- 重连补发的旧录像只关联原来的局，不会占用待归档的新局。无法确认身份或内容冲突的文件保留为冲突档，不覆盖已确认录像。
- 下载时仍核对 YRP 与服务器 EVRP 的种子、时间、文件长度和 SHA-256。只有真实不存在的会话才报告“会话缺失”；校验失败会显示具体会话和拒绝原因。
- 已结束比赛的历史错位可以利用正确冲突档恢复，不改变比分、种子或先后手，不需要重新比赛。恢复工具默认只审计，验证整包导出成功后才允许写入。

服务器上先审计：

```bash
sudo env PYTHONPATH=/opt/ygo-pvp/app /opt/ygo-pvp/venv/bin/python \
  /opt/ygo-evolution/tools/repair_replay_bindings.py \
  /var/lib/ygo-pvp/SESSION_ID.json
```

确认无在线连接后，在维护窗口停止 `ygo-pvp`，再加 `--apply` 执行并重启。工具会备份原会话，保留所有原始录像和冲突文件，拒绝身份不唯一、文件校验失败、未结束或仍有选手连接的会话。不要在服务运行时直接改会话 JSON，服务内存中的旧记录可能覆盖修复。
